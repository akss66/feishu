# ADR-001：MVP 采用模块化单体架构

## 状态

已接受

## 日期

2026-07-20

## 背景

跨境电商飞书情报智能体需要完成定时采集、多语言处理、事件聚合、风险评分、AI 分析、飞书推送和问答。初期只有一个统一日报目标群，来源数量和问答并发有限，团队更需要快速验证信息质量与运营价值，而不是提前解决大规模分布式问题。

## 决策

第一版使用 Python 模块化单体：FastAPI 提供应用入口，APScheduler 负责定时调度，飞书官方 SDK 通过 WebSocket 接收事件，DeepSeek 提供结构化分析。本地使用 SQLite，正式部署使用 PostgreSQL。系统内部按来源、采集、处理、评分、分析、报告、投递和问答划分模块，并通过明确的数据结构交互。

## 备选方案

### 轻量脚本与 Webhook

- 优点：代码量少，上线快。
- 缺点：无法可靠支持用户追问、历史检索、来源健康和失败恢复。
- 未选择原因：只能实现新闻推送，无法满足决策型智能体目标。

### 微服务与消息队列

- 优点：可以独立扩展采集、AI 和推送任务。
- 缺点：部署、监控和故障排查成本显著增加，初期没有足够负载证明其必要性。
- 未选择原因：超出 MVP 需要。

### 无服务器函数

- 优点：无需管理常驻服务器，按调用付费。
- 缺点：长连接、持续网页采集和长时间任务可能受运行时限制，状态管理更复杂。
- 未选择原因：本项目同时需要飞书长连接和持续调度，常驻进程更直接。

## 后果

- 可以用单一部署单元快速交付和调试；
- 模块边界为后续拆分任务队列或独立服务保留空间；
- 正式环境需要一台持续运行的云服务器或云容器；
- 单实例故障会影响全部能力，因此必须增加健康检查、任务重试和数据库备份；
- 当采集任务积压、AI 并发或多租户需求出现时，再评估 Redis、Celery 和服务拆分。
